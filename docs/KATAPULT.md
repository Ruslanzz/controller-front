# Обновление прошивки по CAN через Katapult

Загрузчик [Katapult](https://github.com/Arksine/katapult) (бывший CanBoot)
занимает первые 8 КБ flash и позволяет заливать приложение по шине CAN, без
ST-Link. Здесь — настройки под **эту** плату и порядок работ.

> **Статус: не проверено на железе.** В окружении, где готовились изменения,
> нет ARM-тулчейна и доступа к реестру PlatformIO, поэтому ни Katapult, ни
> приложение собрать не удалось. Всё ниже выведено из исходников Katapult и
> схемы платы; первый прогон делайте с подключённым ST-Link.

## Почему без загрузчика по CAN не обойтись

Встроенный в кристалл ROM-загрузчик STM32F103 работает **только через
USART1** — CAN в нём нет (он появляется лишь у линейки F105/F107). На этой
плате штатный загрузчик недоступен вдвойне:

- **BOOT0** притянут к GND через R14 (10 кОм) и не выведен ни на один разъём;
- на XP2 выведен только **USART1 TX** (PA9), а **RX (PA10) не разведён** —
  говорить с ROM-загрузчиком нечем.

ST-Link по XP1 (NRST / SWCLK / SWDIO / GND / 3V3) остаётся аварийным входом:
что бы ни случилось с загрузчиком, плата всегда перешивается через SWD.

## Настройки Katapult (`make menuconfig`)

```
Micro-controller Architecture .... STMicroelectronics STM32
Processor model ................. STM32F103
Build Katapult deployment app ... (выключено)
Clock Reference ................. 8 MHz crystal
Application start offset ........ 8KiB bootloader
Communication interface ......... CAN bus (on PA11/PA12)
CAN bus speed ................... 125000
GPIO pins to set on bootloader entry .... !PA15
Support bootloader entry on rapid double click of reset button .... (по вкусу)
```

Два пункта, без которых работать не будет:

- **`CAN bus speed = 125000`.** Шина узла настроена на 125 кбит/с: APB1
  36 МГц, предделитель 18 → 2 МГц, 16 TQ на бит (1 + BS1 13 + BS2 2).
  Значение появляется в меню только при включённом `Low-level options`.
- **`INITIAL_PINS = !PA15`.** На плате CAN-трансивер имеет вход **STB**
  (`CAN_STB`, PA15), и вывести его из режима ожидания можно только низким
  уровнем. Katapult об этом не знает; без этой строки он поднимет CAN, но
  трансивер останется спать и на шине не будет ничего. Восклицательный знак
  означает «выставить в ноль».

Сборка и заливка загрузчика (один раз, через ST-Link):

```sh
make menuconfig
make
# out/katapult.bin -> 0x08000000
st-flash --reset write out/katapult.bin 0x08000000
```

## Сборка приложения под загрузчик

```sh
pio run -e katapult          # приложение с 0x08002000
pio run -e bluepill_f103c8   # обычная сборка под ST-Link, с 0x08000000
```

Окружение `katapult` включает `-D USE_KATAPULT_BOOTLOADER` и подставляет
`ldscript/stm32f103c8_katapult.ld`. В нём два отличия от штатного скрипта:

- `FLASH` начинается с `0x08002000` (первые 8 КБ — загрузчик);
- **вершина стека опущена до `0x20004FF8`.** Katapult держит сигнатуру
  запроса в последних 8 байтах ОЗУ. Если оставить стек на `0x20005000`,
  `NVIC_SystemReset()` затрёт сигнатуру собственным push, и узел уйдёт в
  обычную перезагрузку мимо загрузчика — «то входит, то не входит».

Приложение переносит таблицу векторов само (`Bootloader_RelocateVectors()`
первой строкой в `main()`).

> Прошивка из окружения `katapult` **не стартует без загрузчика**: на
> `0x08000000` должен лежать Katapult. Для заливки напрямую через ST-Link
> берите `bluepill_f103c8`.

## Уход в режим обновления

Ведущий шлёт кадр `StdId 0x171` (`BASE_BOOT + BOOT_COUNT` от device_id 0x01):

| байт | значение |
|---|---|
| 0 | адрес узла (`0x04` для этого узла) |
| 1..4 | сигнатура `0x4B 0x54 0xB0 0x07` |

Узел кладёт сигнатуру Katapult в ОЗУ и перезагружается. Сигнатура в кадре
нужна, чтобы случайная помеха не увела контроллер в загрузчик на ходу:
**свет гаснет сразу и не вернётся до конца обновления**, поэтому команду
подавайте только на стоящей машине.

Если приложение не отвечает (например, залита битая прошивка), Katapult всё
равно останется в режиме загрузчика: он не находит корректного приложения и
не прыгает в него.

## Заливка

```sh
python3 ~/katapult/scripts/flash_can.py -i can0 -q          # найти узлы
python3 ~/katapult/scripts/flash_can.py -i can0 -u <UUID> \
        -f .pio/build/katapult/firmware.bin
```

Скорость: при 125 кбит/с реально выходит ~6–8 КБ/с, образ на 30 КБ заливается
за 5–8 секунд.

## Идентификаторы на шине

Katapult занимает:

- **0x3f0 / 0x3f1** — служебный канал (обнаружение узлов, назначение адреса);
- **0x200 + 2·N** и **+1** — рабочие адреса узлов в режиме прошивки
  (`CANBUS_NODEID_OFFSET = 128` в `flash_can.py`: `id = node_id·2 + 0x100`).

С прикладным планом адресации (`StdId = (device_id << 8) | (base + index)`)
это не конфликтует: узлы передают 0x131 / 0x141 / 0x161 (ведущий), 0x241
(задний), 0x441 (передний), а приём в каждом узле отфильтрован по
`std_device_id == MASTER_DEVICE_ID`, так что кадры Katapult игнорируются.

Тем не менее **прошивать лучше при обесточенном ведущем**: он держит шину
циклом кадров каждые 20 мс, а на 125 кбит/с это лишний трафик во время
заливки. Если когда-нибудь появится узел с device_id 0x02 или 0x03,
использующий адреса 0x200–0x203, сдвиньте `CANBUS_NODEID_OFFSET` в
`flash_can.py` так, чтобы адреса уходили в свободный диапазон 0x600+.

## Что проверить при первом запуске

1. Залить Katapult через ST-Link, **не заливая приложение**. Узел должен
   отвечать на `flash_can.py -q` — это проверяет и скорость шины, и что
   `!PA15` действительно разбудил трансивер.
2. Залить приложение `-e katapult` по CAN и убедиться, что оно стартует
   (габариты загораются, идёт телеметрия 0x441).
3. Проверить возврат в загрузчик кадром 0x171 из работающего приложения.
4. Только после этого повторять на остальных узлах.

## Аварийное восстановление

ST-Link по XP1 работает всегда. Полное восстановление:

```sh
st-flash erase
st-flash --reset write out/katapult.bin 0x08000000
```

Чтобы кривое приложение не могло затереть загрузчик, можно закрыть страницы
0–7 аппаратной защитой записи (option bytes). Тогда даже ошибочная работа с
flash из приложения оставит путь к обновлению живым.
